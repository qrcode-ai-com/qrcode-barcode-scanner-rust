This folder prepares the Artifact Hub listing of the container image `ghcr.io/qrcode-ai-com/qrcode-barcode-scanner`, versions 0.11.0, 0.12.0, 0.12.1 and 0.12.2. Artifact Hub reads a container listing from the annotations of an image index, and from a small metadata file stored in the same registry repository. Nothing here rebuilds an image: each listing names the two published platform manifests of its version by digest. The 0.11.0 listing is live on [Artifact Hub](https://artifacthub.io/packages/container/qrcode-barcode-scanner/qrcode-barcode-scanner).

The [QR code scanner](https://qrcode-ai.com/en-US/qr-code-scanner) and the [barcode scanner](https://qrcode-ai.com/en-US/barcode-scanner) let you try the engine in a browser first. To run the image with a mounted file, read the [QR code scanner Docker guide](https://qrcode-ai.com/en-US/qr-code-scanner/docker) and the [barcode scanner Docker guide](https://qrcode-ai.com/en-US/barcode-scanner/docker).

To make a test image with a known payload, use the [QR code generator](https://qrcode-ai.com/en-US/qr-code-generator) or the [barcode generator](https://qrcode-ai.com/en-US/barcode-generator), and keep the payload you encoded to compare it with the scan.

## 0.12.2: the version tag is the listing

The index of 0.12.2 carries the listing keys itself, as the indexes of 0.12.1 and 0.12.0 do. [release-0.12.2.json](../docker/v0.12.2/release-0.12.2.json) holds them as `index_annotations`: the eight OCI annotations of the images, plus creation time `2026-11-27T19:01:10.229552395Z` (the build time of the later of the two images, later than `0.12.1`), license `MIT`, vendor, keywords, logo, maintainer and the address of [LISTING.md](LISTING.md) at commit `b2a9dc2259faaaeee8439e895ffb4fece372e621`. `oci-publish.yml` writes that index under the tag `0.12.2` after both platform images, so `0.12.2` is both the newest package version and the listing tag. Artifact Hub picks it as the latest version because it is created after `0.12.1`. The images themselves keep only their eight OCI labels.

Artifact Hub reads the page of a tag once. The page of `0.12.2` is therefore LISTING.md as that commit holds it, which names qrscan 0.12.2 and the tag `0.12.2`; the pages of `0.12.1` and `0.12.0` stay the ones their own indexes name.

Artifact Hub also scans the images of a package for known vulnerabilities and shows the count on the package page. The 0.12.2 image is built on a base of seven packages, and its recipe exports an image only when the pinned scanner lists no finding in it. Artifact Hub uses its own scanner version and the database of its day, so its count is its own: the [container guide](../docker/v0.12.2/README.md) says what the recipe checked and how the published image is scanned again.

## Why listing tags for 0.11.0

The published index of tag `0.11.0` has eight annotations. It lacks two keys that Artifact Hub needs: `org.opencontainers.image.created` and `io.artifacthub.package.readme-url`. That index is frozen by the release record of the image, so the listing uses listing tags, `0.11.0-r1`, `0.11.0-r2` and so on. Each index names the same two manifests, amd64 `sha256:4dfcdfb66730e191176be72df398e0dadec15ed6dab25227149375fb3931f42c` and arm64 `sha256:8720bf185c698747893fbd67d33bda9f42ffa99ef86af094fbaa7e4a9298a359`. It keeps every original annotation and adds the listing keys: creation time, license `AGPL-3.0-or-later`, vendor, keywords, logo, maintainer and the address of [LISTING.md](LISTING.md) at a fixed commit.

Artifact Hub processes an immutable tag once and keeps the page it read then, so a new page needs a new listing tag. `0.11.0-r1` carried the first page. `0.11.0-r2` carries the page with the Ask AI block and the pictures. From one listing tag to the next, only the page address and the creation time change. Artifact Hub picks the latest version of a container image by its creation time, not by its name, so each tag is created after the one before it: `0.11.0-r1` at the build time of the images, `0.11.0-r2` on the date of its page.

## Files

- [artifacthub-repo.yml](artifacthub-repo.yml): the repository metadata, with the owner and a placeholder for the repository ID.
- [published-index-0.11.0.json](published-index-0.11.0.json): the exact bytes of the published index of tag `0.11.0`, digest `sha256:fd0433f29b0dabd469ce6a8fdcfc7bf6554960301b5bc57b5fca97928fd7cb96`.
- [compose-index.py](compose-index.py): writes the index of a listing tag from those bytes, compares it with the previous listing tag and checks the pushed tag. Its `TAGS` table holds each listing tag and its creation time.
- [LISTING.md](LISTING.md): the page that Artifact Hub shows for the package. Artifact Hub drops every HTML tag and comment of a page and keeps Markdown images, linked or not. So the page holds no HTML: its pictures are Markdown images in their light variant, and `scripts/build-readme-actions.py` writes its Ask AI block with linked badges and the prompt unfolded.

## How it is tested

`compose-index.py --self-test` composes `0.11.0-r1` again from its page commit and checks that it gives the pushed bytes. It composes `0.11.0-r2` and checks that only the page address and a later creation time differ. It refuses an index that is not the published one, a short commit, a tag that is not a listing tag, a change to a manifest or to another annotation, the same page, an earlier creation time and a folder that is not empty. A compose with `--fetch` reads the index, both manifests and both image configurations from the registry anonymously, and every digest, size and creation time must match the pinned values. `scripts/check-packaging-recipes.py` checks that the recorded bytes still hash to the published digest. `scripts/test-readme-actions.py` checks that LISTING.md holds no HTML outside its markers, the 9 assistants, the 5 pictures and the six links of the page.

## Publish it

From 0.12.0 on, once `oci-publish.yml` has published a version tag, `0.12.0`, `0.12.1` then `0.12.2`, and the **public-pull** dispatch on its `oci-v` tag has passed, the owner adds that version tag to the repository in the Artifact Hub control panel. Nothing is pushed by hand.

For 0.11.0, publication is the owner's step. It needs an account that can write to `ghcr.io/qrcode-ai-com/qrcode-barcode-scanner`, the `oras` client and the Artifact Hub account that added the repository. A new page goes under the next listing tag, here `0.11.0-r2`:

1. Merge the page, then note the full 40-character commit of `main` that holds this LISTING.md.
2. Run `python3 distribution/artifacthub/compose-index.py compose --tag 0.11.0-r2 --readme-commit COMMIT --out /tmp/artifacthub-index-r2 --fetch`.
3. Compare it with the previous listing tag: `python3 distribution/artifacthub/compose-index.py compare-pushed --tag 0.11.0-r1 --expect /tmp/artifacthub-index-r2/index.json`.
4. Push the index under the new tag: `oras manifest push --media-type application/vnd.oci.image.index.v1+json ghcr.io/qrcode-ai-com/qrcode-barcode-scanner:0.11.0-r2 /tmp/artifacthub-index-r2/index.json`.
5. Check the pushed tag: `python3 distribution/artifacthub/compose-index.py verify-pushed --tag 0.11.0-r2 --expect /tmp/artifacthub-index-r2/index.json`.
6. In the Artifact Hub control panel, edit the repository and add the tag `0.11.0-r2`. Artifact Hub processes only the tags listed there, ten at most.

The first listing tag also added the repository. In the Artifact Hub control panel, the owner added a repository of kind "Container images", name `qrcode-barcode-scanner`, display name "QR Code & Barcode Scanner", URL `oci://ghcr.io/qrcode-ai-com/qrcode-barcode-scanner`, and the tag `0.11.0-r1`. Then the owner put its repository ID in artifacthub-repo.yml and pushed the file under the tag `artifacthub.io`: `oras push ghcr.io/qrcode-ai-com/qrcode-barcode-scanner:artifacthub.io --config /dev/null:application/vnd.cncf.artifacthub.config.v1+yaml artifacthub-repo.yml:application/vnd.cncf.artifacthub.repository-metadata.layer.v1.yaml`. A new listing tag leaves that metadata as it is.

The email in artifacthub-repo.yml must be the email of the Artifact Hub account that adds the repository. Users who need the original tag can still pull `0.11.0`, which holds the same image.

## What it reads

<p align="center">
  <a href="https://github.com/qrcode-ai-com/qrcode-barcode-scanner-rust#supported-formats">
    <picture>
      <source media="(prefers-color-scheme: dark)" srcset="https://raw.githubusercontent.com/qrcode-ai-com/qrcode-barcode-scanner-rust/main/docs/assets/brand/formats-dark.gif?v=92fa0e8084df">
      <img src="https://raw.githubusercontent.com/qrcode-ai-com/qrcode-barcode-scanner-rust/main/docs/assets/brand/formats-light.gif?v=bdfe5fc5f9b3" alt="The code families the engine reads: QR codes, matrix and stacked codes such as Data Matrix, retail barcodes such as EAN-13, and other linear barcodes such as Code 128" width="100%">
    </picture>
  </a>
</p>

The same engine reads every destination’s images, so codes of different formats in one image come back in one report.

- QR: QR Code, Micro QR, rectangular Micro QR (rMQR)
- Matrix and stacked: Data Matrix, Aztec, PDF417, MaxiCode
- Retail: EAN-13, EAN-8, UPC-A, UPC-E
- Other linear: Code 128, Code 39, Code 93, Codabar, ITF, GS1 DataBar, GS1 DataBar Expanded, Telepen

The engine’s [supported formats](https://github.com/qrcode-ai-com/qrcode-barcode-scanner-rust#supported-formats) section states the known limits.
